# CI for a LinkML schema repository

Two workflows, copied from `assets/` and adapted:

- **`validate.yml`** — on every push and pull request, lint the schemas and annotate problems
  inline on the PR diff.
- **`release.yml`** — on a `v*` tag, generate every artifact and attach it to a GitHub release.

Both use [`NeverBlink-OSS/linkml-scala-action`](https://github.com/NeverBlink-OSS/linkml-scala-action),
which bundles the engine as pure Node. **Do not install the binary in CI** — no Docker, no JVM, no
download step, and it works on Linux, macOS and Windows runners.

## Before writing anything

Find out what you are working with, rather than assuming a layout:

```shell
ls .github/workflows/                       # what already exists
find . -name '*.yaml' -not -path './.git/*' | head -30
grep -rl "^classes:\|^slots:\|linkml:types" --include='*.yaml' . | head
```

You need three answers:

1. **Where are the schemas?** This becomes `files:`. Globs including `**` work.
2. **Do they use `imports:`?** If so you must pass `imports:` too, or generation fails on the
   import resolution.
3. **Which artifacts do consumers need?** Do not generate all six by default — ask. Generating
   things nobody consumes is noise that will rot.

If a workflow already exists, add to it rather than creating a competing one.

## Validation

```yaml
- uses: actions/checkout@v7
- uses: NeverBlink-OSS/linkml-scala-action@v0.14.0
  with:
    files: "schemas/**/*.yaml"
```

Fatal and error problems fail the step. Warnings are reported but do not fail unless you set
`strict: true` — worth recommending for a schema that is published, since warnings here mean
missing `tree_root` and similar things that degrade generated output.

Problems appear as GitHub annotations on the *Files changed* tab, which is the main reason to use
the action rather than the CLI.

Useful inputs:

| Input | Purpose |
|---|---|
| `files` | Schemas to process. Space/newline separated, globs incl. `**`. **Required.** |
| `strict` | Treat warnings as failures. |
| `imports` | Directory holding schemas referenced by `imports:`, keyed by path. |
| `ignore` | Newline-separated substrings of problems to silence. Use sparingly. |
| `annotations` | Set `false` to suppress inline annotations. |
| `working-directory` | Base for resolving the three paths above. |

`ignore` is a footgun: it silences by *substring match on the message*, so
`ignore: "Unknown reference"` hides every unknown reference, including new ones. Prefer fixing
the schema. If it must be used, scope it as narrowly as possible and leave a comment saying why.

## Generation

```yaml
- uses: NeverBlink-OSS/linkml-scala-action@v0.14.0
  with:
    command: generate
    generator: json-schema      # json-schema | shacl | rdfs | linkml | frictionless | scala
    files: "schemas/**/*.yaml"
    output: build/json-schema
```

One output file per input schema, named after it (`person.yaml` → `person.schema.json`). The
`scala` and `frictionless` generators emit several files per schema, so those land under
`output/<schema-name>/`.
Omit `output` and the result goes to the job log, which is occasionally what you want for a
quick diff but usually not.

Use a matrix rather than repeating the step:

```yaml
strategy:
  matrix:
    generator: [json-schema, shacl, rdfs]
```

### Resolving imports

If a schema says `imports: [common/types]`, point `imports` at the directory containing
`common/types.yaml`:

```yaml
with:
  files: "schemas/main.yaml"
  imports: "schemas"
```

Getting this wrong is the most common CI failure for multi-file schemas, and the error message
is about a missing element rather than a missing import — so check it explicitly.

## Releases

`assets/release.yml` triggers on `v*` tags, generates each artifact, and attaches everything to
the release. Two things make it trustworthy:

- **Validate before generating.** A release built from a schema with warnings is a bad release.
  The template validates with `strict: true` first, and the generate job depends on it.
- **`contents: write`** is required to create the release, and is the only elevated permission
  needed. Do not add more.

The template uses `softprops/action-gh-release`, pinned to a major version. If the repository
already has a release process, integrate with it instead of adding a second one.

Consider also attaching the **derived schema** (`generator: linkml`) — imports resolved and slots
materialised into a single self-contained file. It is the most useful artifact for downstream
consumers, because they need no import resolution and no LinkML tooling to read it.

Out of scope for these templates, and worth naming so nobody assumes otherwise: publishing docs
to GitHub Pages (linkml-scala has no Markdown generator), breaking-change detection between
versions, and publishing to npm or PyPI. Say so if the user expects them.

## Versioning the action

There is no moving `@v1` tag. The action is released once per linkml-scala release and carries
the same version number, so always pin an exact tag such as `@v0.14.0`. That pins the engine and
the LinkML implementation along with it, which is what you want when generated artifacts are
committed or published.

Check what the current release is before writing a workflow — the tag list is at
<https://github.com/NeverBlink-OSS/linkml-scala-action/releases>, or
`gh release list -R NeverBlink-OSS/linkml-scala-action`. Bumping it is a one-line change, so
Dependabot or Renovate handles updates fine if the repository already runs one.

## Verify before you finish

Do not hand over an unverified workflow. Check the YAML parses, and run the same commands
locally so you know the globs and imports resolve:

```shell
python3 -c "import yaml,sys;[yaml.safe_load(open(f)) for f in sys.argv[1:]];print('YAML OK')" \
  .github/workflows/validate.yml .github/workflows/release.yml

linkml-scala validate --strict $(find schemas -name '*.yaml')     # same check as CI
linkml-scala generate json-schema --to /tmp/out schemas/main.yaml # same generation as CI
```

If `gh` is available and the workflow is pushed, `gh run list` and `gh run view --log-failed`
close the loop properly.

## Templates

`assets/validate.yml` and `assets/release.yml`. Copy them into `.github/workflows/` and edit the
`files`, `imports` and generator list — they are starting points, not drop-ins. Full CLI flags,
which map onto the action's inputs, are in `linkml-scala <command> --help`.
